# Кейс: лид-студия «Тихий свет»

## Задача

Показать, как помощник на основе языковой модели может поддержать менеджера магазина при обработке текстовых обращений: выделить потребность, сопоставить её с каталогом и подготовить черновик для проверки человеком.

Проект выполнен как локальный демонстрационный прототип на примере магазина светильников. В репозитории нет данных о внедрении у реального заказчика, продажах или измеренном сокращении времени работы.

## Пользователь и сценарий

Пользователь — менеджер магазина. Он вставляет сообщение или загружает `.txt`, получает текстовую сводку и карточку, проверяет каталог и видит вопросы для уточнения. Затем открывает просмотр черновика и отдельно подтверждает сохранение.

На примере запроса 12 ламп при остатке 8 приложение сохраняет исходную потребность 12 шт. и показывает нехватку 4 шт. Желаемый срок не превращается в подтверждённую дату поставки, а расчётная сумма не означает, что заказ можно исполнить.

## Что реализовано

| Решение | Зачем оно нужно бизнесу |
| --- | --- |
| Карточка по строгой схеме и проверка чисел | Делает результат модели пригодным для дальнейшей обработки |
| Отдельные блоки сообщения, каталога и расчёта | Позволяет менеджеру проверить источник каждого существенного сведения |
| Точный поиск по демонстрационному каталогу | Не подменяет отсутствующий товар случайным аналогом |
| Расчёты в коде | Даёт воспроизводимые суммы и расхождения |
| Просмотр перед сохранением | Оставляет решение за менеджером |
| Проверка версии и защита от повторов | Отклоняет устаревшие данные и не дублирует одну операцию |
| Локальное хранение черновиков | Позволяет показать полный сценарий без внешней базы |

## Что демонстрирует проект

- Проектирование процесса с участием человека: модель предлагает результат, приложение проверяет данные, менеджер подтверждает действие.
- Интеграцию с Responses API: структурированные ответы и полный цикл вызова разрешённых функций.
- Разделение интерфейса, извлечения данных, каталога, расчётов и хранения.
- Обработку ошибок доступа, квоты, частоты запросов и ожидания ответа.
- Проверку критичных сценариев отдельным тестовым транспортом без расхода средств API.
- Подготовку исходников, инструкции, контрольных примеров и проектных скиллов для передачи.

## Подтверждённый результат

16 ноября 2026 года прошли 20 автоматических тестов. Они проверяют расчёты, структуру данных, подтверждение, актуальность карточки и повторные операции. Контрольный расчёт: 70 800 ₽ при бюджете 60 000 ₽, превышение 10 800 ₽, нехватка 4 шт.

Это проверка кода и сценариев с тестовым транспортом. Работа настоящей модели, её доступность в конкретном аккаунте и качество извлечения сведений не подтверждались этим прогоном. Подробности — в [отчёте](VERIFICATION.md).

## Как показать заказчику

Начните с [главного README](../README.md), затем покажите интерфейс по [сценарию демонстрации](DEMO.md). Для обсуждения интеграции откройте [архитектуру](ARCHITECTURE.md). Не обещайте показатели эффективности без отдельного измерения на согласованной выборке обращений.

Возможное развитие обсуждается как отдельный объём работ: подключение каталога заказчика, внешняя CRM, роли сотрудников, размещение и эксплуатация. Эти возможности в текущей версии не реализованы.
